# Проверка кадра локальной vision-моделью

Документ фиксирует, как LLM встраивается в сценарий осмотра. Главный принцип:
модель **не ставит диагноз** и не измеряет. Она отвечает на один узкий вопрос —
«видны ли на кадре признаки, которые подтверждают или опровергают гипотезу
датчиков». Диагноз формирует движок правил, модель лишь даёт визуальное
подтверждение.

## Сценарий

1. QR на агрегате → карточка оборудования.
2. Сервер считает телеметрию и выдаёт **гипотезы** (правила: износ подшипника,
   кавитация, утечка, ослабление крепления и т.д.) с evidence.
3. Инженер наводит камеру на узел.
4. Сервер вырезает зону узла по ArUco-привязке и отправляет в локальную
   vision-модель:
   - кроп зоны,
   - список гипотез по этому узлу,
   - перечень визуальных признаков, которые нужно проверить.
5. Модель возвращает строгий JSON: подтверждает / опровергает / не видно.
6. Итоговый статус: гипотеза датчиков + визуальное подтверждение. Если модель
   и эвристики расходятся — статус «требуется проверка», а не «дефект».

## Контракт

```
POST /vision/check
{
  "equipment_id": "PUMP-001",
  "component_id": "pump",
  "image_b64": "<jpeg>",          // или multipart, если удобнее
  "hypotheses": ["bearing_wear", "cavitation"],
  "signs": ["коррозия", "подтёк масла", "трещина", "отслоение краски"]
}
```

Ответ:

```json
{
  "component_id": "pump",
  "verdict": "confirmed | refuted | insufficient",
  "confidence": 0.0,
  "observations": [
    {"sign": "коррозия", "visible": true, "area_pct": 18, "note": "бурые пятна на корпусе"}
  ],
  "matches_hypothesis": ["bearing_wear"],
  "explanation": "1–2 предложения на русском",
  "model": "qwen2.5vl:3b",
  "latency_ms": 0,
  "grounded": true
}
```

Правила:
- `verdict=insufficient`, если узел не в фокусе, перекрыт или темно.
- `area_pct` — грубая оценка доли площади, не измерение.
- Запрещено возвращать числовые значения датчиков, сроки и диагнозы.
- `grounded=true` только если модель ссылается на видимые детали кадра.

## Защита от галлюцинаций

1. **Узкий вопрос вместо открытого.** Не «что здесь не так», а «виден ли признак X».
2. **Обязательный «не видно».** Модель должна уметь отказаться; отсутствие ответа
   не считается подтверждением.
3. **Сверка с эвристиками.** Если эвристики дают высокий score, а модель — нет,
   статус «требуется проверка», а не «норма».
4. **Сверка с гипотезой датчиков.** Если датчики молчат, модель не может одна
   поднять severity до `critical`.
5. **Температура 0, JSON-схема, повторная попытка при невалидном JSON.**
6. **Логирование.** Каждый вызов сохраняется с картинкой, промптом и ответом —
   для разбора на защите и для честного ответа на вопрос «почему решили, что дефект».

## Ограничения, которые говорим жюри

- Модель компактная (3B), работает на ноутбуке в контуре предприятия.
- Она **не заменяет** дефектоскопию и не измеряет геометрию.
- Качество на реальных дефектах не валидировано: нет размеченного датасета.
- Поэтому вердикт модели — подтверждающий сигнал, а не приговор.
- Всё офлайн: модель лежит локально, наружу не уходит ни один байт.

## Почему не «сценарий»

Сценарии симулятора нужны только чтобы показать срабатывание правил по датчикам.
Визуальная проверка — не сценарий: модель каждый раз смотрит на конкретный кадр
и может ответить «не видно». Это принципиально разные вещи, и на защите это
стоит проговаривать.
