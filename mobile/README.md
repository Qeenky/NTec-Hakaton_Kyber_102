# NTec Инспектор — мобильный помощник инженера

Android-клиент к локальному серверу NTec: **QR на агрегате → карточка оборудования →
AR-осмотр → результат → сохранение в историю**. Работает в изолированной локальной
сети, без интернета и облачных сервисов.

## Экраны

| Экран | Файл | Что делает |
|---|---|---|
| Подключение | `lib/screens/settings_screen.dart` | IP:порт сервера, `GET /health`, сохранение в `shared_preferences`, подсказки про точку доступа и USB |
| Старт / QR | `lib/screens/scanner_screen.dart` | `mobile_scanner`, код вида `PUMP-001` → `GET /equipment/{code}`, ручной выбор из `GET /equipment` |
| Карточка | `lib/screens/equipment_screen.dart` | паспорт, наработка, срок, узлы с цветовым статусом, активные диагностики, телеметрия за 5 минут (`fl_chart`) |
| AR-осмотр | `lib/screens/ar_inspection_screen.dart` | превью камеры, оверлеи `/ws/frame`, OCR, баннеры диагностик, живые значения `/ws/telemetry`, «Снять кадр» и «Загрузить фото» |
| Узел | `lib/screens/component_detail_screen.dart` | паспорт узла, оценка ресурса, последняя проверка, рекомендация |
| Результат | `lib/screens/inspection_result_screen.dart` | найденные зоны/дефекты, evidence, рекомендации, `POST /inspections` |
| История | `lib/screens/history_screen.dart` | `GET /inspections?equipment_id=...` |

Индикатор связи (`GET /health` раз в 10 с) — в шапке каждого экрана.

## Оформление

- Тёмная промышленная тема, фирменный синий КСТ: заливки `#135AA6`,
  акцент/текст на тёмном `#4C9EEA`, живые данные `#35B8E0`; нейтральная шкала
  `#0A0E13 / #121820 / #1B2430 / #2E3A48`; текст `#F5F8FB`, вторичный `#A9B7C6`.
- Семантика: норма `#4ADE80`, внимание `#FBBF24`, дефект `#F87171`,
  нет данных `#94A3B8`.
- Типографика: экран 22, блок 14–15, текст 14–15, подпись 12, метрика 24–30.
  Минимальный размер текста — 11.
- Отступы — шкала 4/8/12/16/24 (`AppSpacing`), единые `Panel`, кнопки и чипы.
- Все цвета собраны в `lib/theme/app_theme.dart`; по экранам хардкода цветов нет.

## Адрес сервера

1. Запустите backend:

   ```powershell
   cd ..\backend
   .\.venv\Scripts\Activate.ps1
   uvicorn app.main:app --host 0.0.0.0 --port 8000
   ```

2. **Wi-Fi (основной режим).** Включите на ноутбуке мобильную точку доступа Windows.
   Телефон подключается к ней, сервер слушает `0.0.0.0:8000`, в приложении укажите
   `192.168.137.1:8000` (значение по умолчанию). Интернет не нужен.
3. **USB (резерв).** Подключите телефон кабелем и выполните:

   ```powershell
   adb reverse tcp:8000 tcp:8000
   ```

   В настройках приложения укажите `127.0.0.1:8000` (кнопка «Подставить адрес для USB»).
4. Windows Firewall: разрешите входящие TCP 8000 для частной сети:

   ```powershell
   New-NetFirewallRule -DisplayName "NTec backend" -Direction Inbound `
     -LocalPort 8000 -Protocol TCP -Action Allow -Profile Private
   ```

Готовые APK:

### Важно: кириллица в пути

Проект лежит в `D:\NTec-Хакатон`. Debug-сборка это переживает, но **release AOT
(`gen_snapshot`) не читает файлы по пути с кириллицей**. Поэтому release собран из
временной копии с ASCII-путём:

```powershell
$dst = "$env:TEMP\opencode\ntec_release_build"
robocopy . $dst /E /XD build .dart_tool .git .idea
cd $dst
flutter pub get
flutter build apk --release
```

Готовый `app-release.apk` скопирован в `mobile/dist/`. Если будете собирать release
сами — повторите этот перенос или используйте путь без не-ASCII символов.

### NDK и Gradle

* Шаблон Flutter 3.50 требует NDK `28.2.13676358`, но в окружении его нет.
  Приложение не содержит нативной сборки, поэтому в `android/app/build.gradle.kts`
  указан установленный `27.3.13750724`. Flutter печатает предупреждение о версии NDK —
  на сборку и работу это не влияет.
* В `android/gradle.properties`:
  * `android.overridePathCheck=true` — иначе AGP отказывается собирать проект в пути с кириллицей;
  * `kotlin.incremental=false` — иначе Kotlin падает на закрытии инкрементальных кэшей на Windows;
  * `android.newDsl=false`, `android.builtInKotlin=false` — из шаблона Flutter.
* `shared_preferences_android` зафиксирован на `2.4.28` через `dependency_overrides`:
  версия 2.5.x тянет `jni` с нативной сборкой (NDK 28 + CMake), которая в этом окружении не нужна.
* Release подписан debug-ключом (так в шаблоне Flutter). Для защиты этого достаточно;
  для публикации нужен свой keystore.

## Как устроен AR-осмотр

* `camera`: `ResolutionPreset.medium` (720p), `ImageFormatGroup.yuv420`.
* YUV420 → RGB → JPEG (quality 80) в отдельном isolate (`lib/services/frame_codec.dart`),
  не чаще ~4 кадров/с. Кадр поворачивается по `sensorOrientation`, AR-экран
  зафиксирован в портретной ориентации.
* JPEG уходит бинарным сообщением в `/ws/frame?equipment_id=...`.
* **Загрузить фото** — `image_picker` (Android Photo Picker, без доступа к
  хранилищу). Фото декодируется как есть, EXIF-ориентация применяется,
  длинная сторона больше 1600 px пропорционально уменьшается до 1600,
  кодирование JPEG quality 90. Соотношение сторон не меняется.
  Затем `POST /analyze?equipment_id=...` multipart с полем `image`.
  Ответ разбирается как `/ws/frame`: оверлеи рисуются на статичном фото.
  Ошибки 404/413/415/422 и ошибки декодирования показываются понятным текстом
  с кнопкой «Повторить».
* Загруженное фото показывается через `BoxFit.contain` (letterbox, без обрезки)
  в области над нижней панелью; оверлеи пересчитываются по `image_width`/
  `image_height` ответа сервера и фактическому масштабу/смещению картинки.
* Полигоны приходят в пикселях отправленного кадра. `ArOverlayPainter` пересчитывает
  их в экранные координаты с учётом `BoxFit.cover` и обрезает по верхней границе
  нижней панели, чтобы подписи не уходили под кнопки.
* Если сервер не ответил за 3 с — плашка «нет ответа», отправка и переподключение
  продолжаются. При обрыве WebSocket — переподключение через 2 с с индикатором
  «Переподключение…».
* Все REST-запросы и сохранение осмотра повторяются при сетевых ошибках/5xx:
  до трёх повторов с паузами 300 / 700 / 1500 мс.
* Тап по узлу в карточке или по видимому полигону в AR открывает детальную
  карточку узла. «Последняя проверка» берётся из `GET /inspections`.
* **AI-проверка узла** — кнопка рядом с «Снять кадр» и «Загрузить фото».
  Отправляет последний JPEG в `POST /vision/check?equipment_id=...&component_id=...`
  (multipart, поле `image`), таймаут 30 с. Пока модель работает, показывается
  «Модель смотрит кадр…», кнопки блокируются.
  Если в кадре несколько видимых узлов — компактные чипы выбора (по умолчанию
  первый видимый). Результат: вердикт и цвет (`defect` / `no_defect` /
  `insufficient`), четыре признака с `есть` / `нет` / `не видно`, комментарий,
  уверенность, время ответа, модель и подпись «Локальная модель, работает без
  интернета». Полная карточка открывается снизу, на экране остаётся строка-итог.
* **AI-заключение** на экране результата: `GET /vision/explain?equipment_id=...`
  при открытии. Показываются `summary`, `actions`, бейдж `severity`, модель и
  время. При `error` — «AI-заключение недоступно» и кнопка повтора, экран работает.
* Если `/analyze` вернул `vision`, он показывается без повторного запроса
  (строка AI-проверки в AR и блок «AI-проверка кадра» на результате).
* **Панель видеоаналитики** в AR (`analytics` из `/ws/frame`): сворачиваемая
  панель над кнопками. Заголовок «Наблюдение · N с · M кадров», строка на узел:
  статус по окну, полоска видимости, подтверждённые дефекты по-русски.
  Отсутствовавшие в окне узлы не скрываются — серые «не в кадре».
  Сортировка: возможный дефект → требует внимания → норма → не в кадре.
  Обновление не чаще 2 раз в секунду, перерисовывается только панель.
* **Видеоаналитика на результате:** таблица по узлам (статус окна, видимость %,
  подтверждённые дефекты), длительность и число кадров. Используется
  `analytics` последнего кадра; в истории — `analytics` сохранённого осмотра
  из `GET /inspections`.
* Если `analytics` нет (старый backend), панель и блок не показываются.
* **Визуальные признаки** (`analytics.components[].signs`): коррозия, подтёк
  масла, окисление контактов, отслоение краски, механическое повреждение,
  трещина/скол, отсутствие кожуха. В AR-строке узла показываются `detected`
  (красный/оранжевый) и `single_observation` (серый, «единичное»);
  `not_detected` и `not_visible` не засоряют панель. На результате и в карточке
  узла — таблица «признак / статус / уверенность / кадры» и строка
  «Не проверено» для `not_visible`. Если `signs` нет — блок скрыт.
* **Верх AR-экрана** — только тонкая строка статуса: точка связи,
  «кадр N · F к/с», «видно N из M» и кнопка журнала. Баннеры, диагностики,
  рекомендации, признаки и ошибки сверху не показываются.
* **Нижняя панель AR**: OCR, телеметрия, аналитика и единый сворачиваемый блок
  «Диагностик: N · Признаков: M» (по умолчанию свёрнут; развернул — видны
  тексты, рекомендации и признаки). Ошибки AI-проверки и анализа фото — только
  в нижней панели и журнале, без всплывающих карточек.
* **Геометрия оверлеев:** кадр с камеры центрально обрезается под фактический
  аспект превью, поэтому координаты сервера и превью относятся к одному кадру.
  Пересчёт в экран — через `OverlayMapping` (cover/contain, letterbox/crop),
  с обрезкой по виджету и границам нижней панели.
* **Потеря привязки:** при `board.detected=false` оверлеи не рисуются, в строке
  статуса — «привязка потеряна». При `board.stale=true` полигоны полупрозрачные
  (30%), тонкий пунктир, без подписей, статус — «привязка ослаблена». Узлы,
  вышедшие за кадр больше чем на 20% площади, не рисуются. Через 1.5 с без
  свежей позы оверлеи скрываются.
* **Журнал событий**: потеря/восстановление привязки, смена планшета,
  появление/исчезновение признака, срабатывание/снятие диагностики,
  обрыв/восстановление связи, AI-проверка, ошибки. Новые сверху, в памяти до
  500 записей, обновление не чаще 2 раз/с. Кнопка-иконка в строке статуса
  открывает шторку (время, кадр, тип, сообщение). Журнал передаётся в результат,
  показывается свёрнутым блоком и отправляется в `POST /inspections` полем
  `events` (старый backend поле игнорирует).
* **Итог осмотра (`verdict`)**: на результате и в истории показывается статус
  `defects_found` / `attention_required` / `insufficient_data` /
  `no_visible_defects` с цветом, причина, списки «Проблемные узлы» и
  «Не были видны в кадре» и обязательный дисклеймер.
  Если серверного `verdict` нет, он вычисляется на клиенте по
  `components_status` и `analytics`: проблемы → «Требуется проверка»;
  при нехватке данных или невидимых узлах — «Недостаточно данных», но никогда
  не «норма». В списке истории — компактный бейдж, в раскрытом осмотре — тот же блок.
* «Видно N из 5 узлов» — в шапке AR и на результате. У невидимых узлов
  показывается «не в кадре», значения не подставляются (—).
* Остаточный ресурс везде помечен как оценка: `≈ 2.5 лет · оценка`.
* **Резерв:** кнопка «Снять кадр» делает `takePicture()`, применяет EXIF-ориентацию,
  отправляет один кадр и показывает оверлеи на замороженном изображении.
  «Вернуться к потоку» возобновляет стриминг.
* Если камера недоступна, осмотр всё равно можно завершить и сохранить: сервер
  подставит текущую диагностику, детекций будет 0.

## Ограничения

* На телефоне (Samsung A03, Android 13) подтверждены экраны, связь и сохранение
  осмотра. Не проверены на устройстве: загрузка фото через Photo Picker, тап по
  оверлею, обрезка подписей под нижней панелью, фактический FPS и нагрев.
  Логика и парсинг покрыты тестами.
* Release APK собран из временной ASCII-копии; исходники в `mobile/` те же.
* `POST /analyze` проверен на живом сервере (`frame_01.jpg`): 200, планшет
  найден, 5 полигонов, `image_width/height=1280×960`. В ответе нет `frame_id` —
  клиент показывает «загруженное фото» и не отправляет `frame_id` при сохранении.
* `POST /vision/check` проверен на живом сервере: 200, `qwen2.5vl:3b`, вердикт
  `no_defect`, 4 признака, ~12 с. `GET /vision/explain` вернул `warning`,
  summary/actions. `/analyze` отдаёт последний `vision` в поле `vision`.
* `analytics` проверен на живом `/ws/frame`: текущий компактный формат
  (`visible_ratio`, `confirmed_defects`) разбирается; новый формат с
  `status_window`/`visibility_ratio` поддержан. Панель и таблица на телефоне
  не проверены.
* Новые AI-экраны не проверены на телефоне: загрузка кадра в модель, чипы
  выбора узла, нижняя карточка результата и AI-заключение. Логика и парсинг
  покрыты тестами, эндпоинты проверены curl’ом.
* На телефоне проверены базовые экраны и сохранение осмотра (Samsung A03,
  Android 13). Новые сценарии — загрузка фото, тап по узлу, обрезка оверлеев —
  требуют повторного прогона на устройстве.
* Оверлеи рисуются по последнему ответу сервера; при потере связи остаются
  последние координаты и включается плашка «нет ответа».
* Повтор `POST /inspections` после таймаута может создать дубль осмотра:
  идемпотентного ключа в API нет. На практике локальный сервер отвечает быстро.
* Приложение не делает никаких сетевых запросов, кроме адреса из настроек.
