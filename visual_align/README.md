# visual_align — привязка зон к кадру **без маркеров**

На реальном производстве ArUco-планшета не будет — есть только камера и оборудование.
Модуль привязывает размеченные зоны узлов к кадру по **совмещению с эталонным
изображением**: эталон один раз описывается локальными признаками, на кадре ищутся
те же признаки, по инлайерам RANSAC-ом считается гомография «эталон → кадр», и
полигоны зон переносятся этой гомографией. Маркеры не детектируются и не декодируются.

```
visual_align/
  aligner.py                 FeatureAligner, AlignmentResult, Smoother, save/load
  dataset.py                 синтетические кадры с истинной H, негативы, перекрытие
  viz.py                     отрисовка зон, соответствий, HUD
  scripts/eval.py            полный замер -> report.json + samples/
  scripts/build_reference.py фото + разметка -> models/<name>.npz
  tests/                     pytest: регистрация, отказ, hold, save/load, EMA
  models/                    готовые эталоны .npz (изображение + зоны + дескрипторы)
  samples/                   6 визуализаций
  data/negatives/            3 реальных фото без эталона (для теста ложных срабатываний)
  report.json                фактические метрики
```

## Как это работает

`FeatureAligner.register(frame_bgr) -> AlignmentResult`:

1. **Подготовка.** Кадр → grayscale → CLAHE (локальное выравнивание освещения).
   Эталон тоже хранится с CLAHE, поэтому дескрипторы сопоставимы при разной засветке.
2. **Быстрый отказ.** Если `std(gray) < 4` (почти однородная поверхность) или
   найдено < 30 признаков — сразу `None`, без попыток подогнать гомографию.
3. **Два детектора.** ORB (`nfeatures=4000`) и AKAZE (`MLDB`, threshold 0.001)
   работают независимо и параллельно (два потока). Для каждого:
   - `BFMatcher` с нормой под дескриптор (ORB и AKAZE-MLDB — `NORM_HAMMING`),
     `knnMatch(k=2)` + Lowe ratio **0.75** (+ отсечка distance ≤ 80 для ORB);
   - `cv2.findHomography(..., RANSAC, 3.0)`, затем уточнение по инлайерам и
     пересчёт инлайеров относительно финальной H.
4. **Выбор.** Побеждает вариант с максимумом инлайеров (при равенстве — по
   inlier_ratio и ошибке репроекции). В замере реально побеждают оба:
   ORB 22/30, AKAZE 8/30.
5. **Проверки правдоподобия** (защита от ложных гомографий на «чужом» кадре):
   - `inliers >= 15` и `inlier_ratio >= 0.25` (настраивается);
   - `det(H[:2,:2]) > 0` — без зеркал; проекция планшета конечна, выпукла,
     площадь 5–600 % кадра, соотношение сторон ≤ 6, центр внутри проекции;
   - инлайеры не в куче: выпуклая оболочка ≥ 1 % кадра и разброс ≥ 12 % кадра
     по обеим осям;
   - **NCC** (нормированная кросс-корреляция) эталона и кадра в области
     перекрытия ≥ 0.30 — главный фильтр ложных срабатываний.
6. **Уверенность** (0..1), формула задокументирована в `aligner.py`:

   ```
   term_inliers = min(1, inliers / 60)
   term_ratio   = min(1, inlier_ratio / 0.60)
   term_reproj  = exp(-median_reproj_px / 5)
   confidence   = 0.50*term_inliers + 0.30*term_ratio + 0.20*term_reproj
   ```

7. **Удержание позы.** Если кадр не прошёл проверки, а предыдущая поза валидна
   не дольше `hold_seconds=1.5`, возвращается она же с `stale=True` и `age_sec`;
   уверенность линейно падает к концу окна. Дальше — `None`.

`project(zones=None, smooth=True)` берёт последнюю валидную (в т.ч. удержанную)
гомографию и возвращает `dict[str, list[[x, y], ...]]` в пикселях кадра.
`Smoother` — EMA по углам полигонов, `alpha=0.35`, как в `ar_board`.

`save()`/`load()` кладут изображение, зоны и **предвычисленные** дескрипторы в
`models/<name>.npz` (без pickle), так что повторный запуск не пересчитывает
признаки. Сборка эталона из 4961×3508 занимает ~0.8 с, файл ~0.5 МБ.

## Ограничения (честно)

1. **Это верхняя граница.** Кадры отрендерены из того же файла, что и эталон:
   та же текстура, тот же ракурс «в плоскости». Реальной съёмки оборудования в
   репозитории нет (демо-видео — запись экрана приложения). На реальном фото
   будут блики, неравномерная резкость, отличие печати от файла — ожидайте рост
   ошибки до единиц пикселей и падение успеха; порог `min_ncc` придётся
   откалибровать на 10–20 реальных кадрах.
2. **Нужна текстура.** Гладкий крашеный корпус без надписей/крепёжа даст мало
   признаков — модуль вернёт `None`. Это by design, но для таких узлов нужен
   либо маркер, либо отдельная текстура/наклейка на оборудовании.
3. **Диапазон.** Проверено: поворот ±20°, масштаб 0.6–1.6, наклон до 25°,
   перекрытие до 1/3. За пределами — не гарантируется.
4. **Освещение.** CLAHE спасает от общей темноты и градиента, но не от
   пересвета/бликов на глянце и не от motion blur.
5. **Похожие эталоны.** Если два одинаковых агрегата стоят рядом, гомография
   может «прилипнуть» к чужому. Нужен выбор эталона по QR/номеру или
   ограничение зоны поиска.
6. **Скорость.** ~100 мс p50 на CPU — это ~10 fps, не 30. Для backend-анализа
   кадров достаточно; для 30 fps на телефоне нужен downscale/трекинг между
   кадрами (следующий шаг, не сделан). p95 нестабилен (124–254 мс между
   прогонами) из-за конкуренции потоков ORB и AKAZE за общий пул OpenCV;
   при `parallel=False` p50 ~178 мс, но p95 стабильнее (~203 мс).
7. `FeatureAligner` хранит состояние (hold, smoother) — **не потокобезопасен**;
   один экземпляр на поток/камеру.

## Как подготовить эталон для реального оборудования

1. Снять 1 резкий кадр с рабочей позиции камеры (1280×720+, хороший свет,
   без смаза). Желательно — тот же ракурс, что будет на демо.
2. Разметить зоны узлов полигонами **в пикселях этого кадра**. Годится
   `ar_board/annotate.py` (формат `components[].polygon_px`) или любой
   редактор, сохраняющий JSON:
   `{"zones": {"motor": [[x,y], ...], "pump": [[x,y], ...]}}`.
3. Собрать эталон:

   ```bat
   .venv\Scripts\python.exe scripts\build_reference.py ^
       --image D:\frames\pump_001.jpg ^
       --zones D:\frames\pump_001_zones.json ^
       --name pump_001 --out models\pump_001.npz
   ```

4. Проверить на 5–10 кадрах с разных углов/освещения: смотреть `confidence`,
   `stale`, ошибку на видимых углах зон. Если есть ложные отказы — снизить
   `min_ncc` до 0.22–0.25; если ложные позы — поднять до 0.35–0.4.
5. Хранить эталон на `equipment_id`; при перестановке камеры/оборудования
   пересобрать.

## Встраивание в backend

```python
from visual_align import FeatureAligner

aligner = FeatureAligner.load("visual_align/models/pump_001.npz")  # один раз

def analyze(frame_bgr, ts):
    result = aligner.register(frame_bgr, timestamp=ts)
    if not result.ok:
        return {"ok": False, "reason": result.reason}
    zones = aligner.project()          # dict[str, list[[x, y]]] в пикселях кадра
    return {
        "ok": True,
        "stale": result.stale,         # True -> UI рисует оверлей приглушённо
        "age_sec": result.age_sec,
        "confidence": result.confidence,
        "method": result.method,       # orb | akaze
        "homography": result.homography.tolist(),
        "zones": zones,
    }
```

`result.to_dict()` уже отдаёт JSON-совместимый словарь (включая `homography`,
`inliers`, `stale`, `reason`) — можно класть прямо в ответ API. Дальше зоны
используются так же, как в `ar_board`: crop по полигону → детекторы дефектов/
манометра → вердикт. `register` никогда не бросает исключение на плохом кадре:
худший случай — `homography=None`.

## Вердикт

- **Демо — да, условно.** Если эталон — тот же планшет/файл, что показывают в
  кадре (или заранее снятый кадр с той же позиции), привязка стабильна:
  100 % успеха, ~0.5 px, отказы на мусоре, удержание позы 1.5 с. Это честная
  замена маркерам в сценарии «камера смотрит на тот же объект».
- **Продакшен — пока нет.** Нужны реальные кадры оборудования, калибровка
  `min_ncc`, проверка бликов/перекрытий, выбор эталона среди похожих агрегатов
  и ускорение (downscale + трекинг). Маркеры/QR стоит оставить как fallback и
  как способ выбрать нужный эталон.
