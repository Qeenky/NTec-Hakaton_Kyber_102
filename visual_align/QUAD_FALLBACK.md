# Quad-fallback: привязка по контуру печатного листа

## Зачем

Признаковая привязка (ORB/AKAZE + RANSAC) ломается, когда планшет занимает
меньше ~50% кадра: на маленьком листе слишком мало текстурных точек, и
`findHomography` либо не набирает инлайеров, либо опирается на компактный
кластер (фото узла) и отбраковывается проверкой разброса.

Но на стенде планшет — это **светлый печатный лист A3 на тёмном фоне**.
Его контур видно даже на 18% кадра. Отсюда второй, независимый способ:
найти четырёхугольник листа и построить гомографию по четырём углам.

## Как работает

`visual_align/quad.py` → `detect_sheet_quad(frame)`:

1. кадр → grayscale → уменьшение до 512 px по длинной стороне (рабочий размер);
2. Otsu-бинаризация; если средняя яркость «белого» класса меньше «чёрного» —
   маска инвертируется (лист должен быть светлее фона);
3. морфология: `close` (заполняет дырки от текста и фото) + `open` (убирает мусор);
4. `findContours(RETR_EXTERNAL)` → `approxPolyDP` (eps = 2% периметра) →
   оставляем выпуклые четырёхугольники;
5. фильтры: площадь 0.2–96% кадра, прямоугольность `contourArea/minAreaRect ≥ 0.72`,
   соотношение сторон `1.414 ± 25%`, заполнение маской ≥ 0.72, контраст
   «внутри минус фон» ≥ 15;
6. лучший кандидат по уверенности.

Гомография: `getPerspectiveTransform(sheet_quad, найденный_quad)`, где
`sheet_quad` — координаты листа **в системе эталона**. Для эталона-обрезка
(фото узла, вырезанное из A3) лист выходит за границы картинки, координаты
отрицательные — это нормально и даёт правильный сдвиг. Если лист повёрнут на
90°, длинная сторона эталона ставится на длинную сторону квада.

Уверенность (0..1), только геометрия:

```
term_rect   = clip((rectangularity - 0.72) / 0.28)
term_area   = clip(area_ratio / 0.20)
term_fill   = clip((fill - 0.72) / 0.28)
term_aspect = exp(-|ln(aspect / 1.414)| / 0.22)
confidence  = 0.30*term_rect + 0.25*term_area + 0.20*term_fill + 0.25*term_aspect
```

После построения H проверяется фотометрия: эталон warp-ится в кадр и
считается NCC (`quad_low_ncc` при < 0.30). NCC — главный барьер от ложных
срабатываний: «белый прямоугольник» с посторонним содержимым геометрию
проходит, а фотометрию — нет. Итоговая уверенность домножается на
`0.65 + 0.35*max(0, ncc)`.

Публичный API:

* `FeatureAligner.register_by_quad(frame, timestamp=None) -> AlignmentResult`
  (`method="quad"`, `inliers=0`, есть `ncc`, `confidence`, `timings_ms["quad"]`);
* `visual_align.detect_sheet_quad(frame) -> QuadDetection` — чистая детекция;
* `Reference.sheet_quad` / `sheet_quad_from_rect(board_size, rect)` — геометрия
  листа; `FeatureAligner.from_files(..., sheet_rect=(x0, y0, x1, y1))`.

## Как встроено в реестр

`backend/app/cv/board_registry.py`, `VisualBoardRegistry.register`:

1. признаки по пирамиде эталонов (как раньше) — **приоритет всегда у них**;
2. если результата нет или `inliers < QUAD_FALLBACK_INLIERS = 40` — пробуем
   `register_by_quad` на самом крупном эталоне пирамиды;
3. если quad сработал — он и возвращается; если нет — остаётся слабый
   признаковый результат (лучше, чем ничего);
4. `info()["stats"]` — счётчики `frames / features / quad / quad_attempts /
   no_match`; `info()["quad_fallback"]`, `info()["quad_fallback_inliers"]`,
   `info()["boards"][i]["sheet_rect"]`. Fallback отключается флагом
   `quad_fallback=False`.

Эталоны в `ar_board/references.json` — это **обрезки** листа
(`photo_rect_px`), поэтому реестр при загрузке определяет, где обрезок лежит
на полном A3: ищет `*/layout.json` с совпадающим по размеру `photo_rect_px`,
проверяет содержимое по NCC и вычисляет `sheet_rect` в координатах эталона.
Старые `.npz`-кэши без этой геометрии тоже работают: `sheet_rect`
переопределяется при загрузке.

## Цифры

Синтетика `test_photos/_scale_*.jpg` (лист A3 на тёмном фоне, 1280×720).
«Проход» = валидная поза **и** ошибка углов эталона < 8 px (истина — яркая
маска листа). `features` — один эталон-обрезок, ORB+AKAZE; `реестр` — реальная
пирамида ORB (1600…160) + quad, как в `VisualBoardRegistry`.

| 18% | нет / 0 / — | 0.90 / 1.85 px | quad | quad |
| 25% | нет / 0 / — | 0.96 / 2.09 px | quad | quad |
| 35% | нет / 0 / — | 0.97 / 1.82 px | quad | quad |
| 50% | нет / 0 / — | 0.97 / 1.99 px | quad | quad |
| 70% | нет / 0 / — | 0.96 / 2.79 px | quad | features, 1.74 px |
| 90% | да / 27 / 15.43 px | 0.99 / 2.16 px | quad | features, 1.36 px |

Итоги:

* features: `ok` 1/6 (только 90%), «точно» 0/6; в реальной пирамиде ORB —
  2/6 (70% и 90%, ошибка 1.4–1.7 px, 161–266 инлайеров);
* quad: 6/6 (ошибка 1.8–2.8 px, NCC 0.90–0.99);
* гибрид: 6/6 = **100%** (цель ≥ 90%), ошибка ≤ 2.8 px;
* ложные срабатывания: **0/20** на `datasets/pumps/normal/*` (20 случайных,
  seed 7) — и на уровне aligner-гибрида, и на уровне реестра. Сырой детектор
  контура на этих фото не сработал ни разу (0/20); отдельный тест проверяет,
  что белый прямоугольник с посторонним содержимым отсекается по NCC.

Латентность (медиана/95-й перцентиль, 15 прогонов после прогрева, кадр с
листом на 50%):

| кадр | quad | features (ORB+AKAZE) | features ORB-only (прод) |
|---|---:|---:|---:|
| 480×720 | 7.4 / 10.1 мс | 44.7 / 87.5 мс | 29.0 / 32.6 мс |
| 1280×720 | 7.5 / 12.0 мс | 103.6 / 177.4 мс | 50.4 / 53.0 мс |

Бюджеты выполнены: quad ≤ 15 мс, features ≤ 120 мс (медиана). Рабочий размер
детекции — 512 px по длинной стороне (было 640: на 480×720 не укладывались
в 15 мс).

Тесты: `visual_align` — 15 (10 старых + 5 новых на quad), `backend` — 132
(127 старых + 5 новых на fallback/счётчики). Все зелёные.

## Ограничения

* **Только светлый лист на тёмном фоне.** Otsu + контраст «внутри минус фон»
  рассчитаны на стенд с печатным A3. На реальном оборудовании (металл, блики,
  произвольный фон) метод не применим — там нужна детекция планшета/объекта
  (модель или поиск по шаблону), а не контур.
* Лист должен быть четырёхугольником с соотношением сторон около A3
  (1.06–1.77). Квадратный лист или другой формат отвергается, пока не задан
  `expected_aspect` (в `detect_sheet_quad`) / `sheet_rect` нужных пропорций.
* У quad нет инлайеров и ошибки репроекции: уверенность геометрическая,
  точность ограничена контуром (на синтетике 1.8–2.8 px; на реальной печати
  добавятся изгиб бумаги, неравномерная засветка и дисторсия объектива).
* Для эталона-обрезка нужна геометрия листа (`sheet_rect`). Если её не
  передать и не удалось вывести, quad не «придумывает» позу: соотношение
  сторон эталона (1.0) не совпадёт с A3, и кадр будет честно отвергнут.
* Quad — спасение, а не замена: при инлайерах ≥ 40 всегда выбираются признаки.
  При отказе признаков реестр всё равно прогоняет всю пирамиду (5 эталонов),
  поэтому кадр-отказ стоит ~0.2–0.9 с; сам quad добавляет ~7 мс.
* `backend/app/cv/pipeline.py` (вне зоны правки) по-прежнему пишет
  `board.method = "features"` для feature-режима. Разделение по методам видно
  в `VisualBoardRegistry.info()["stats"]`.

## Изменение в проверке разброса инлайеров

`min_inlier_spread` по каждой оси снижен с 12% до 10% кадра: на маленьком
планшете корректная поза может опираться на текстуру только в области фото
узла (компактный кластер). Это починило пограничный синтетический кадр
(seed 11: ошибка позы 0.38 px, но разброс 11.2% по X). Защита от совсем мелких
кластеров осталась, а основной барьер от ложных поз — NCC.
